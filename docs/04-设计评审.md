## 2. 设计评审

### 2.1 分层与职责

| 层 | 职责 | 关键文件 | 评价 |
|---|---|---|---|
| 主进程 | 窗口/菜单/单文件 KV 真源/文件 I/O | `main.js`、`kv-store.js`、`ipc-handlers.js`、`file-io.js` | 边界清晰，A− |
| preload | 先注入 `global.wx` 再 require utils，contextBridge 暴露 12 项 | `preload.js` | 本次最关键的一招，A |
| 渲染运行时 | WXML 解析、表达式求值、节点级 diff、组件映射、导航、主题 | `wxml-runtime.js`（711 行）、`page-runtime.js` | 自制小程序框架，C+ |
| 页面与数据 | 5 页零复制 + 8 个 utils 零复制 | `src/pages/*`、`src/utils/*` | 逐字节一致，A |
| 工具链 | 复制/转换/校验/探针 | `tools/*.js` | 有效但硬编码，C |

### 2.2 五个关键设计决策

| 决策 | 收益 | 代价 | 结论 |
|---|---|---|---|
| **全局 `wx` polyfill 注入** | 5,060 行 utils + 4 页 JS 一行不改；等价性从人工比对降为机器哈希 | 小程序运行时语义被永久固化，未来升级须再同步 | 本次最优解，长期需抽象 Storage 接口 |
| **主进程单 Map 单文件 KV** | 唯一真源、无写双份、QUOTA 可回滚、`kv:keys()` 单一视图 | 每次 `set` 全文件重写（靠 80 ms 防抖合并缓解） | 合理；分片会破坏 `keys` 视图，暂不该做 |
| **单窗口 5 视图** | 换肤一次改根 class 全局生效；退出 flush 只有一个渲染进程；`getCurrentPages()` 广播天然成立 | 5 页 DOM 常驻；多窗口/多文档需重做 | 合理 |
| **自制 WXML 运行时** | 1700 行 WXML、6444 行 rpx 样式原样复用 | 只覆盖 17 类语法/组件、无行为回归基线、`new Function` 无 sourcemap | 可接受，但必须补行为基线（见 §9 阶段 0） |
| **节点级 diff + 焦点双保险** | 每秒刷时钟不打断输入（B-05 实测：节点/焦点/选区三重不变） | 对**根节点**有效，**循环项通道有缺口**（即 B1 缺陷） | 优点需加限定，不可写成「全面有效」 |

### 2.3 最脆弱的三处耦合

1. **循环项刷新通道**：`createChildren():517` 把 loop 排除出 `rootInsts`，`update():661` 只刷 root，`syncLoop():546` 在数组签名不变时直接 return。**数组整体变化**成了循环项刷新的唯一信号。
2. **`PAGE_IDS` 在 4 处硬编码**（nav / preload / main / verify），加一页要同步四处。
3. **两份 `wx` polyfill + `require` shim**：preload 的 Node 版与渲染的 UI 版语义需人工保持一致，是潜在分叉点。

### 2.4 一条根本张力（本轮最高价值的判断）

小程序原生 `setData` 是**细粒度依赖追踪**；桌面自制 runtime 却以**数组整体变化**作为循环项刷新的唯一信号。

结果：源码作者为性能「刻意不重设数组」的优化（`review.js:251-264`「这样九行不会跟着重绘」、`settings.js:41` 只初始化 `skinList` 一次），**在小程序是优点，在桌面直接变成功能错误**。

这属于**类别问题，不是补一行能根除**——它同时解释了「90/90 全绿却仍有已确认缺陷」，也说明只修 D01 单点不够，必须建立 DOM 行为回归基线。

## 3. 性能评审

### 3.1 量化推算（实测 + 估算）

单篇日记实测：最小 353 B / 真实落盘 413 B / 饱满 2,509 B；8 个配置键合计 432 B。`sendSync` 单次往返 **估算 0.30 ms**（区间 0.20–0.80，未做本机埋点）。

| 篇数 | 冷启动 `kv:get` 次数 | 冷启动耗时（0.20/0.30/0.80 ms） | 写后全量重读 | `store.json` 体积（B/C 口径） | 判定 |
|---|---|---|---|---|---|
| 200（实测） | 223 | 45 / **67** / 178 ms | 201 次 → 60 ms | 0.08 / 0.49 MB | 流畅 |
| 1000（≈2.7 年） | 1,023 | 205 / **307** / 818 ms | 1,001 次 → 300 ms | 0.42 / 2.44 MB | 可感知卡顿 |
| 3650（≈10 年） | 3,673 | 735 / **1,102** / 2,938 ms | 3,651 次 → 1,095 ms | 1.53 / 8.91 MB | 主线程冻结≈1.1 s，接近假死 |

**结论一：容量不是瓶颈，IPC 次数才是。** 写满 10 年也才 8.91 MB，为容量上 SQLite 是错配。
**结论二：第一个可感知点在 1000 篇（约 2.7 年）**，且是「写一次卡一次」——`write()` 成功即失效 5 个 memo，下次 `all()` 又 N 次同步 IPC。
**结论三：架构文档原写「226 次约 20–30 ms」偏乐观 2–3 倍**，实测 223 次、估算约 67 ms，已按实测校准。

### 3.2 启动与内存

- 启动静态资源 635.65 KiB：8 份 CSS 186,936 B + 5 份 WXML 100,287 B + 5 页 JS 99,630 B + 8 utils 264,054 B。
- 启动期 DOM 体量：**1,046 个元素标签**（含文本块约 3,055 节点）、622 处 `{{`（约 576 个绑定点）、**62 个循环指令**。这些计数只说明体量，不参与耗时推算。
- Electron 运行时基线（约 180 MB 二进制）高于原生 Win32/WPF，低于「浏览器 + 本地服务」方案；对日记工具属可接受，但冷启动 1–2 s 是形态固有成本。

### 3.3 优化路径与触发阈值

| 动作 | 触发条件 | 成本 | 风险 |
|---|---|---|---|
| 批量 IPC（`kv:getBatch` / `keysByPrefix`） | 写后回看 ≥300 ms 或 N≥800 | 中 | 要动 `diary-store.js` 或重提已弃用的 preload 镜像 → **触碰「8 utils 零改动」** |
| 配置键 memo 化 + 按 key 精确失效 | 与上同步 | 小 | 同上 |
| 分片存储 | N≥2000 或 `store.json`≥5 MB 或单次 flush≥50 ms | 大 | 破坏 `keys` 单一视图 |
| SQLite/LevelDB | N≥5000 或需事务/全文检索 | 很大 | 引入原生依赖，放弃「运行时零第三方库」 |

## 4. 数据管理评审（本次核心）

### 4.1 存储模型

- 单文件 `%APPDATA%\jiuge-desktop\jiuge-desktop\store.json`，扁平 KV，键名与值结构和小程序逐字一致 → 备份可直读。
- 命名空间物理隔离：`window-state.json`、`.bak`、导入前快照**永不进 Map**，因此不会被 `listDates()` 的前缀扫描误读（实测 `kv:keys()` 无污染）。
- 写时失效缓存 `memoAll/memoWritten/memoStats/memoFreq` **只**在 `write()` 里失效——审计结论：精准，不会因 UI 状态键误触发全量失效；但属约定式一致性，`importBackup` 里的手工补失效是补丁式证据。

### 4.2 可靠性：三道防线 + 三个缺口

**防线**：`store.json.tmp → renameSync` 原子写 + 写前留 `.bak` + 启动解析失败用 `.bak` 恢复并明确提示（不静默清空）+ 导入前快照保留 3 份 + 关窗 flush（`syncWorkReflection → syncStudyNote → persist → stopTimer`，实测回启读回 6/6）。

**缺口（按严重度）**：

| # | 缺口 | 证据 | 后果 |
|---|---|---|---|
| D1 | **无单实例锁** | 全项目 grep `requestSingleInstanceLock` 0 命中；`main.js:238-246` 无条件建窗；`kv-store.js:73-90` 每进程独立 Map | 双击两次 exe，后写者用旧快照整体覆盖 → **永久丢日记、无提示** |
| D2 | **`dispose()` 不 flush** | `kv-store.js:345-347` 只 `cancelTimer()`；`main.js:248-252` `window-all-closed` 直接 quit | 杀进程/断电/崩溃丢失 80–500 ms 内最近一整篇 |
| D3 | **真实 ENOSPC 与模拟路径分叉** | 模拟分支回滚 Map 返回 `QUOTA_EXCEEDED`（`kv-store.js:189-206`）；真实失败走 `CLIENT_EXCEPTION`、不回滚不重试（`:187,267-297`、`preload.js:60-65`） | A5/D7 逐字验过的「本机存储已满…」两条专属文案，**真实磁盘写满时走不到**；数据还留在内存里 |

> D3 是**证据边界问题**，不是产品缺陷：模拟通过≠真实故障已覆盖。

### 4.3 备份与迁移契约

- 桌面导出写 `version=7`；导入兼容 ≥6 及无版本号旧档（`partial=true` 提示「旧版备份」）。
- 8 条冲突策略：本机有正文才跳过 / 空壳允许补写 / 配置类先于写日记（`startedAt` 实测保持 2020-01-01）/ 学习库按 id 合并 / 胶囊去重并跳过非法 openAt / 写后回读复核 / `hasContent` 只认字符串 / 导入同样裁剪 2000·200。
- 文件导入与剪贴板导入**共用唯一 `store.importBackup(text)`**（代码调用各 1 次，桌面层无第二份合并逻辑）——这是本次最值得保留的设计。
- **历史局限**：「只补写不覆盖」没有 `updatedAt` 比较与冲突协商。双端并行写同一天永远不合并且无提示；换机时若新机先写了几天，旧机同日内容被永久跳过，结果只报 `skipped=N`。

### 4.4 容量与迁移阈值

| 篇数 | 体积（真实/饱满） | 建议 |
|---|---|---|
| 200 | 0.08 / 0.49 MB | 现状够用 |
| 1000 | 0.42 / 2.44 MB | 先解 IPC 次数，不要动存储引擎 |
| 3650 | 1.53 / 8.91 MB | 仍远低于 JSON 单文件不适区间；分片/DB 都不划算 |

### 4.5 隐私与数据主权

- 优点：纯本地、零网络、无账号，代码层面 46 个文件 0 命中网络关键字。
- 风险：`store.json` **明文无加密**；卸载不删数据（`deleteAppDataOnUninstall:false`）→ 转让/报废电脑后日记残留；`%APPDATA%` 若被 OneDrive/企业策略重定向，「本地性」不由应用单方面保证；便携版拷 U 盘**数据不跟着走**（`userData` 仍落各机），易被误解。
- 定位说明：这些是「告知与承诺边界」问题，不是 NFR-6 未达成，也不是产品缺陷。

### 4.6 并发与损坏

- 单进程单窗口假设成立时安全；双实例、U 盘多机、网盘同步冲突均无检测。
- 建议：`app.requestSingleInstanceLock()`（~15 行）+ `owner.lock`/mtime 校验 + 文件损坏时只读拒绝写入。

### 6.3 桌面化取舍

左侧竖栏 5 项（设置升为常驻）**优于**原 tabBar；保留原生窗口框 + 应用内变色标题条可接受；`wx:if` 用 `display:none`、picker→select/date、swiper 按 current 显隐——视觉与交互等价，代价是隐藏节点仍占 DOM。滑杆用固定 375 反推 + 真实 `clientX` 两套坐标混用，**「值变了」不等于「变对了」**（缺按档位断言的测试）。

### 6.4 功能过载未因大屏缓解

三模块默认全开、`windowWidth` 锁 375、内容区 900 px 单列居中 → 大屏只带来更宽留白与更长滚动。源评估报告建议的「默认态做减法」只落地成「给用户一个自己去关的开关」，而最不会先去设置页的新用户恰恰最需要默认轻。**这属下一版产品决策，须重新授权**。

### 7.1 证据结构（`verify` 69 项逐项分类）

| 类型 | 条数 | 占比 |
|---|---|---|
| 代码/文本/常量/结构扫描 | 50 | 72.5% |
| 哈希对拍 | 4 | 5.8% |
| 纯 Node 真跑函数 | 15 | 21.7% |
| **Windows GUI 真实运行** | **0** | **0%** |

静态 + 哈希合计 **54/69 = 78.3%**。它们能证明「文件与源项目/设计文档逐字一致」，不能证明「在 Windows 上跑得对」。

### 7.2 覆盖缺口

- PRD §9 主干判据 37 条中，**17 条（45.9%）完全没有桌面真实触发**；形成完整交互闭环仅 **5 条（13.5%）**。
- §4 的 60 项细项里，**41 项（68.3%）只有哈希/静态证据**，被点名的功能簇 20 个（四套模板真实逐套切换、539 条名言散列、导入确认框取消、原生另存为、八段锦动画、滑杆拖拽、单格分析浮层、三大模块面板、复盘三问、胶囊封存倒计时、里程碑增删改、跨零点切日期……）。
- **作用于打包 exe 的功能断言 0 条**：90 条探针跑的是源码版 Electron（日志路径 `file:///G:/.../src/renderer/`），而 `build/electron-run.log` 是 `.../app.asar/...`，**两个不同运行时**。

### 7.3 探针可信度

- 观察者效应**已实证**：探针写入 7 个业务键且未清理；B-28 直接改 `_cells/_workBoard` 私有字段注入「未失焦内容」，随后 `window.__jiugeDirty=false` **主动清脏以避免二次确认弹窗**——该弹窗从未弹出。D6 结论应收缩为「flushAll 被真调用且顺序正确」。
- 共同模式盲区：探针与被测代码共用同一 runtime，`Module._load` 猴子补丁改写产品 require，系统性偏差会被自证为正确。
- `JIUGE_TEST_*` 钩子在 app.asar 内仍在（生产默认关闭正确）。

### 7.4 90/90 与 B1 缺陷的关系

`NoOne` 作为**本轮测试轮次路由**成立（断言全绿、2 轮上限已到）；但作为**发布放行结论**不成立。B1 缺陷正是「用数据层正确 + 零改动哈希代替 DOM 真实行为」这一缺口的教科书级实证。

## 8. 技术债与可维护性

### 8.1 健康度

实现质量 **B（7.6/10）**；技术债健康度 **C（58/100）**——分层 85 / 可读性 78 / 错误处理 52 / 运行时可回归性 45 / 交付可复现性 35 / 再同步成本 48。**债务不在「本次运行」，在「下次改动、换机器、上游升级」。**

### 8.2 Top3 最该还的债

| # | 债务 | 位置 | 成本 | 为什么优先 |
|---|---|---|---|---|
| T1 | **交付可复现三件套**：4 处硬编码源项目绝对路径（`smoke.js` 无 `--source`）；`verify #65` 硬编码 exe 字节/SHA；winCodeSign 7z 绕过无脚本 | `copy-source.js:23`、`wxss2css.js:22`、`verify-equivalence.js:23,977-999`、`smoke.js:19` | 半天 | 干净 clone / CI 必挂；任何重新打包 verify 必掉 68/69 |
| T2 | **`copy-source --pages` 覆盖白名单改写** | `copy-source.js:62-67,122,124` | 一行 `doCopy=false` | 上游升级重跑会静默抹掉设置页导入入口，还自报 18/18 |
| T3 | **`dispose()` 不 flush + B1 循环项刷新** | `kv-store.js:345-347`、`wxml-runtime.js:517/538/546/661` | ~12 行 | ROI 最高的两个 P0 |

### 8.3 上游再同步成本

`copy-source --pages` 对零复制文件幂等、**对白名单文件破坏性**。正确姿势：`--check` 先看 → `--only` 逐页复制 → 手工 rebase `settings` 的 +23/+6 行。两份 SHA256 清单语义不同（`.sha256.json` 整份覆盖、`.copy-manifest.json` 累积不删），而 `verify` **不读清单**、直接实时对拍 → 清单过期不会被发现。

### 8.4 最小改动 SOP

| 改动 | 文件数 | 必须跑 | 坑 |
|---|---|---|---|
| 改桌面层中文文案 | 1 行 + 白名单 1 处 | verify + smoke | 最易漏 `DESKTOP_REQUIRED` 白名单 |
| 改零复制文件文案 | — | 全量重跑 | **成本最高的改动**，等价性证据链全挂 |
| 加「导出 PDF」 | 约 7 文件 / 60–120 行 | 7 条验证 + 完整打包 | 新增 IPC 通道违反 §9.2 |
| 上游升级再移植 | 全 5 页 + settings rebase | copy-check + verify + 打包 | 先 `--check`，禁止裸跑 `--pages` |

### 8.5 干净机器复现

**不能一键复现 L0。** 依赖 4 项未脚本化的本机状态：源项目绝对路径、人工预置的 winCodeSign 缓存、未锁精确 patch 版本、已存在的 `build/`。换机至少 4 次人工介入，且 verify 因 exe SHA 不同必 FAIL。
