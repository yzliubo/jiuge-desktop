## 0. 结论先行

### 0.1 一句话判断

**这份交付的「源码等价性」证据很强，「在 Windows 上跑得对」的证据很弱。可以放心试用、可以判定验收口径内无已发现缺陷；不能据此宣称「生产可用 / 可以放心用」。**

上一轮的 `NoOne` 是**测试轮次路由**（现有断言全部通过、不需要 Engineer 改代码让断言变绿），**不是发布放行结论**。二者被混用，是本次交付最大的证据表述问题。

> **⚠️ 交叉评审后更新（与 software-engineer 核对）**：其 `docs/review/03-实现质量.md` 定位出 3 条 90/90 断言集合外的潜在缺陷，经 QA 独立复核代码**全部成立**。其中第 1 条「循环体内引用外层数据的绑定永不刷新」是**已定位、可复现的产品缺陷**（`setData` 只改外层标量时循环项 DOM class 不刷新），恰好实证了本报告 §1 / §5 的核心论点——**用「数据层正确 + 零改动哈希」代替「DOM / 真实行为正确」会漏掉用户可见缺陷**。因此「产品缺陷 0」应更正为「**现有断言集合内 0 失败；集合外已定位至少 1 个真实缺陷**」。`NoOne` 作为轮次路由仍成立（2 轮上限、不进入第 3 轮），但作为质量结论进一步收紧，详见 §7.1 / §7.3 / §9.2。

## 1. A–F 证据分级覆盖矩阵

### 1.1 分级定义

| 符号 | 等级 | 定义 |
|---|---|---|
| ① | 真实运行验证 | 在真实 Electron / 真实窗口 / 真实文件产物上的行为断言 |
| ② | 代码 / 文本扫描 | 正则、常量、文案、配置、mtime、语法校验等静态检查 |
| ③ | 哈希对拍 | SHA256 / 逐字节一致，只证明「文件相同」 |
| ④ | mock / 模拟 | 纯 Node 内存 `wx`、环境变量注入、运行时 mock、合成 DOM 事件 |
| ⑤ | 仅设计推断 | 只依据架构文档 / README 声明 / 配置项推定 |

「桌面真实触发」列：`●` 完整交互闭环 / `◐` 部分或间接（仅 DOM 结构存在性、启动日志、静态扫描）/ `○` 完全没有。

> 读法：每条取**最强**证据等级。多数判据是「③ 哈希 + ② 扫描 + ④ mock」的组合，但**没有任何组合能推导出「在 Windows 上点下去结果正确」**。

### 2.3 三个结构性风险

1. **验证与实现断链**：15 项行为验证里 10 项跑在内存 `wx` 上，而真实桌面走 `preload → 同步 IPC → 主进程 KvStore（80 ms 防抖 / 原子写 / .bak / QUOTA 回滚）`。若 `wx.getStorageSync` 的 polyfill 在「未命中返回 `''`」「抛错方式」「不可克隆值」上有偏差，哈希扫描与内存 mock 都测不到。零改动 utils 的「正确」是**小程序语义下的正确**，不是桌面语义下的正确。
2. **回归基线不可重复**（详见 §7.3）：`check #65` 把两个 exe 的字节数与 SHA256 写死在脚本里。**只要重新打包一次，exe 内容必变，`verify` 必然从 69/69 掉到 68/69**，除非同步改脚本硬编码和 README §8。这说明 69/69 是**针对当前这两个特定二进制的一次性快照**，不是可重复回归。
3. **78.3% 的静态证据不随环境变化**：在 Windows、macOS、甚至只有文件的机器上跑 `verify`，只要文件不变，结果都一样。它测的是「文件」，不是「Windows 上的运行」。

> 补充：`smoke` 28 项、`bench` 4 项同样是纯 Node 内存 `wx`（`bench` 注入 200 篇到内存 Map，非真实 `store.json` 文件），`copy-source --check` 18 项是逐字节对拍，`wxss2css --check` 是文本残留扫描。**五套脚本合计 124 项断言，Windows GUI 真实运行断言为 0。**
